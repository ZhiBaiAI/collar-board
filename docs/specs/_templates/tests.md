# 测试文档 — ⟨模块名⟩ / ⟨功能名⟩

> **本文件是 [spec.md](./spec.md) 的伴生文档，不是第五种变更类型。**
> 变更类型仍然只有四种：feature / patch / sunset / blueprint。
> 本文件回答一个问题：**这个功能点的每条验收标准，靠什么测出来。**
>
> 跨功能点的测试知识（分层口径、运行时机、冒烟清单）不在本文件，
> 见 [docs/runbook/testing.md](../../../runbook/testing.md)。
>
> ⚠️ **本文件是模板**：`./spec.md` 等相对链接要**复制到功能点目录后**才成立，
> 在 `_templates/` 原地看必然悬空——这不是断链，别去"修"。

| 项 | 值 |
|---|---|
| 关联 Spec | [spec.md](./spec.md) |
| 负责人 | ⟨@谁⟩ |
| 创建 / 更新 | ⟨YYYY-MM-DD⟩ / ⟨YYYY-MM-DD⟩ |

## 0. 怎么用（三条规则）

1. **每条 AC 至少有一个测试点。** spec §5 的 `AC-N` 与本文件的「对应 AC」列必须对得上——
   有 AC 却没测试点，就是「验收标准不可测试」的实锤。
2. **每个测试点必须回指一条 AC**（探索性测试除外，需在「测什么」里写明探索目标）。
3. **改代码同时改本文件。** 测试点变了、缺口变了，都在「变更记录」留一行。

**AC 编号规则**（决定「对应 AC」列怎么写）：

| 来源 | 编号形态 | 例 |
|---|---|---|
| spec.md §5 验收标准 | `AC-N` | `AC-1`、`AC-2` |
| `PATCH-NNN-*.md` §⑥ 验收标准 | `AC-P⟨NNN⟩-N` | `AC-P001-1` |

> 两套编号刻意分开，**同一目录下不能撞车**。
> 主文档只给意图时（如「超过上限就截断」），具体数值常由 patch 确定——
> 此时测试点应回指 **patch 的编号**，因为只有那一条具体到可断言。

> **最小可用形态**：功能点简单时，只需第 1 节的前三列 + 一行缺口。
> 不要为了填满模板而编造测试点——**没有的测试点写进「已知缺口」，比伪造覆盖更有价值。**

## 1. 测试点清单

| 编号 | 层级 | 测什么 | 对应 AC | 代码位置 | 状态 |
|---|---|---|---|---|---|
| TC-1 | ⟨unit / integration / e2e / manual⟩ | ⟨给定 X，当 Y，则 Z⟩ | AC-1 | ⟨`src/…` 或 `—`⟩ | ⟨已实现 / 未实现 / 手工验证⟩ |
| TC-2 | | | AC-2 | | |

层级口径见 [testing.md 分层词汇表](../../../runbook/testing.md)——
**同一件事全项目只用一个层级名，不要自创。**

**覆盖核对**（落盘前逐条过）：

- [ ] spec §5 每条 `AC-N` 都至少出现在「对应 AC」列一次
- [ ] 没有指向不存在的 `AC-N`
- [ ] `未实现` 的测试点都已在第 3 节登记缺口

## 2. 测试数据与 fixtures

| 项 | 内容 |
|---|---|
| 数据集 | ⟨造数脚本 / 固定 fixture / 从预发脱敏拉取，写明来源⟩ |
| 边界值 | ⟨本功能点特有的边界，如 pageSize 上限、超时临界值⟩ |
| 隔离要求 | ⟨是否需要独立库 / 事务回滚 / 清理钩子⟩ |
| 禁止事项 | ⟨如：不许连生产库、不许依赖真实第三方⟩ |

## 3. 已知缺口

> **这一节是给下一个人看的**——他知道哪里没测、为什么没测、该找谁。
> 留空 = 声称完全覆盖，请先确认这不是错觉。

## 4. 变更记录

| 日期 | 触发 | 测试点变化 | 链接 |
|---|---|---|---|
| ⟨YYYY-MM-DD⟩ | ⟨feature 初版 / PATCH-NNN / 缺陷修复⟩ | ⟨新增 TC-3 / 删除 TC-2（原 AC 已 sunset）⟩ | ⟨patch 链接 或 —⟩ |

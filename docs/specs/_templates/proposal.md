# PROPOSAL-NNN：⟨一句话标题⟩

> **提案 ≠ 变更类型。** feature/patch/sunset/blueprint 描述「规格怎么演进」，
> Proposal 描述「**未经审阅的改动怎么安全落库**」。
> 适用：非研发角色（测试/产品/设计）、AI 的大改动、任何无 commit 权限参与者。

| 项 | 值 |
|---|---|
| 提案人 | ⟨@谁 + 角色（产品/设计/测试/AI 辅助）⟩ |
| 目标模块 | `⟨spec.md⟩`（新功能则先走 [wiki 蓝图](../../wiki/blue-print/README.md)） |
| 状态 | `待审阅` → `已通过` / `已驳回` |
| 创建 / 更新 | ⟨YYYY-MM-DD⟩ / ⟨YYYY-MM-DD⟩ |

---

## 1. 需求（想达成什么）

⟨用户视角描述，不写实现。产品经理能填、AI 能读懂。⟩

## 2. 已验收净改动（Net Diff）

> 只放**验收过的净改动**，不含探索过程中的写删往返。
> diff 以 `diff --stat` + 关键片段形式贴入，完整 diff 指向分支/沙箱。

```diff
⟨文件路径⟩
- 旧逻辑
+ 新逻辑
```

## 3. 决策记录（多轮对话中的关键取舍）

| 决策点 | 选择 | 理由 |
|---|---|---|
| ⟨例：接口返回结构改不改⟩ | ⟨改/不改⟩ | ⟨一句话⟩ |

## 4. 验收证据

- ⟨截图 / 测试结果 / 「所见即所得」确认记录⟩
- ⟨影响面：动了哪些模块 / 接口 / 数据 / 配置⟩

## 5. 审阅结论（由 dev 角色填写）

| 项 | 值 |
|---|---|
| 准入检查 | ⟨问题匹配 ✓ / 范围受控 ✓ / 复用 ✓ / 可逆 ✓⟩ |
| 结论 | ⟨通过 → cherry-pick 净改动并转为 feature/patch；驳回 → 理由⟩ |
| 审阅人 | ⟨@谁⟩ |
| 落库动作 | ⟨转为 PATCH-NNN / 合入 spec.md 章节 / 新建 feature⟩ |
| 日期 | ⟨YYYY-MM-DD⟩ |

---

## 规则

1. **提案不直接落库** —— 通过后由 dev 角色智能应用（cherry-pick 净改动），转为对应变更类型并登记。
2. **提案可独立阅读** —— 与 patch 同理，不依赖读者先读 spec。
3. **驳回不删除** —— 驳回理由是决策上下文，标注后保留。
   **写给未来的读者**：不保留理由，下个会话的 Agent（或换了人的团队）会把
   同一个被否方案当新方案重新提一遍；理由就是「这个提议已被否过，因为 X」的路障。
4. **净 diff 必须可验证** —— 无验收证据的提案不予审阅。

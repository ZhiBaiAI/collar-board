# ADR-0001：冲突检测放在预发集成态，不在编码态做监控

| 项 | 值 |
|---|---|
| 状态 | accepted |
| 日期 | 2026-09-09 |
| 决策者 | 模板预置 |
| 相关 Spec | [[讨论稿]哨兵机](../../wiki/blue-print/[讨论稿]哨兵机.md) |

## 背景

多人高速迭代下，「隐形冲突」（各自分支全绿、合并后才现形）指数增长。
直觉解法是尽早介入：读取每个人本地编码阶段的输入与 Agent 输出，
在编码阶段就把冲突扼杀（即 Agent Manage / nekocollar-app 方案——
一个全局 codeAgent 信息采集器，监听 cursor / claude code 等进程的输入输出）。

实际跑下来**失败**，两个致命问题：
1. **噪音太多、信噪比极低**——release 前的本地编码态充满写了又删、试了又改的探索，「过程态」绝大部分是无用噪音。
2. **成本过高**——监控本地编码态输入输出 token 消耗惊人，各 Agent 行为监控也难做（工具、习惯人各不同）。

## 决策

**我们不做编码态监控，把冲突检测的介入时机后移到预发集成态**（哨兵机方案，
见相关蓝图）。

## 备选方案

| 方案 | 优势 | 代价 |
|---|---|---|
| **预发集成态检测（选定的）** | 信噪比高（参考有效发现率 >70%）；还原「谁的开发机都没有的」合并态 | 需独立机器 + 云端 Agent；发现晚于编码 |
| 编码态全量监控（Agent Manage） | 理论上最早发现 | 噪音大、token 成本高、信噪比不可用 |
| 什么都不做（只靠 CI） | 零成本 | 语义冲突测不出，隐患延续到线上 |

## 理由

编码态是「**意图尚未定型**」的阶段，此时**信息熵最高、确定性最低**，
用它做冲突检测成本过高、噪音淹没信号。
而 **release 集成分支是「冲突唯一会现形的地方」**——
检测就应该 24 小时盯着这个地方。

## 后果

- **正面**：本地进程零依赖可长期稳定；参与者不被监控、无隐私顾虑；告警只在真有合并风险时发。
- **负面**：冲突发现晚于编码阶段（接受——早期发现的价值被噪音成本抵消）。
- **必须接受的代价**：哨兵机存在维护成本；信号命中前团队需忍受一段「无哨兵」窗口期。
- **上下文影响**：无风险——检测发生在独立机器的工作区镜像上，不动任何人的本地环境。

## Revisit 条件

- 项目回到单人/单仓开发（冲突面消失）→ 可以撤掉哨兵机。
- 出现分钟级自动集成流水线且能承载语义检测 → 介入时机可以重新前移评估。

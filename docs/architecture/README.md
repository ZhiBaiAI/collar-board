## 目录约定

```
docs/architecture/
├── README.md                 # 本文件：结构视图（必须短）
├── principles/               # 工程原则：跨场景不变量（幂等/一致性/超时/降级/兼容）
│   └── P-NNN-原则名.md       # 一页一个原则
└── ADR/
    └── NNNN-简述.md          # 架构决策记录，四位编号，只增不改
```

**结构视图只写现在时事实**——模块依赖、接口契约、数据模型描述「系统此刻怎样运转」。
演进过程（什么时候改的、为什么改）属于 ADR 与 changelog，不写在这里。
判定口诀：**写「X 依赖 Y」，不写「X 从 Z 改成了 Y」。**

### ADR 的归档标准：未来决策价值，不是字数或年龄

归档（移入 `_archived/` 或标注 deprecated）看**这条记录还能阻止未来的错误决策吗**：

- **归档**：理由已失效（被 supersede）、或决策已成常识无需专门记录
- **保留**：未来有人再问「为什么不用 XX」时，还答得上来——
  短不等于该归档（248 词的决策也可能仍在指导取舍），长不等于该留（533 词也可能只是历史）

## 工程原则（principles/）与 ADR 的分工

| | 本文件（结构视图） | principles/ | ADR/ |
|---|---|---|---|
| 回答 | 系统此刻**怎样运转**（事实） | 这类问题**永远**怎么处理（不变量） | 当时**为什么**这么选（因果） |
| 时态 | 只写现在时 | 只写现在时 | 记录过去，只增不改 |
| 变更 | 随结构同步 | 极少变；变了是大事，另起 ADR 记录 | 随选型持续演进 |

原则与 ADR 冲突时，**先改原则再改实现**——原则是决策的上游。
每条原则须含：来源、最后确认时间、适用范围（与其他知识条目同规格）。
模板：[_template-principle.md](principles/_template-principle.md)。

## 什么值得写 ADR

只记**不可逆或代价高昂的决策**。判断标准：
**未来有人问「为什么不用 XX」时你能拿出来回答的，就值得记。**

值得：选数据库、定通信协议、引入新中间件、拆分服务、确定状态机模型。
不值得：变量命名、目录微调、换个工具函数。

## 上下文缝补检查（每次架构变动必做）

任何架构变动都要问：**这次改动会不会让 AI 看不到某些东西？**

| 变动类型 | 风险 | 缝补方式 |
|---|---|---|
| 提示词 / 配置外置到平台或 DB | AI 读不出行为逻辑，推理链断裂 | 只读 MCP 通道 + 配套 Skill |
| 逻辑外置到脚本平台 | 脚本内容不在仓库 | `//!` 声明式注释保留锚点 |
| 引入环境差异 | 排查时遇到无法解释的现象 | AGENTS.md 显式声明 + ADR 记录细节 |
| 代码生成 / 编译期魔法 | 源码 ≠ 运行态 | 生成物可读化，runbook 给出还原方式 |

> **铁律：任何导致上下文异常的研发架构变动，都必须用适合的方式缝补缺损的上下文。**

未缝补 = 架构缺陷，必须在 ADR 的「后果」里显式登记为技术债。
完整协议见 [runbook/context-stitching.md](../runbook/context-stitching.md)。

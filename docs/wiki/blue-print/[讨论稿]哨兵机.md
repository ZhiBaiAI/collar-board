## 1. 问题定义

效率上来之后，**人与人之间对新输入的上下文交换效率成了瓶颈**：
我上午改了接口签名，你下午改了前端调用——各自本地都跑得通，
合到预发业务逻辑一冲突，甚至很久之后才炸。

这种「隐形冲突」在多人高速迭代下指数增长，是 AI 研发质量劣化的头号杀手。
接口签名、共享配置槽位 key、DB 字段变更、并发时序——
这类冲突**在任何单一开发分支上都「一定不存在」，必须等集成后才现形**。

不解决：团队不敢加速。不解决别的：单机工具无法还原「所有人最新提交合在一起」的环境。

## 2. 现状与调研

| 对象 | 做法 | 优劣 | 来源 |
|---|---|---|---|
| 编码态全量监控（Agent Manage） | 本地 app 监听所有 Agent 进程输入输出，提前判别冲突 | ❌ 信噪比极低、token 成本惊人 | [ADR-0001](../../architecture/ADR/0001-冲突检测介入时机.md) |
| CI 合并后测试 | 合入主干才跑测试 | ❌ 发现太晚，且测不出「语义冲突」（签名对但行为矛盾） | 常规实践 |
| 独立哨兵机 | 独立机器还原预发合并态 + Agent 冲突分析 | ✅ 业界实践报告有效发现率 >70%，每周揪出 40+ 隐形问题 | [实践文章](https://www.bestblogs.dev/article/62c701cf52) |

## 3. 候选方案

| 方案 | 思路 | 优势 | 代价 | 结论 |
|---|---|---|---|---|
| 编码态监控 | 监听每个人本地 Agent 输入输出 | 理论上最早发现 | 噪音大、成本高、介入时机错误 | 否决（ADR-0001） |
| **预发集成态检测（哨兵机）** | 独立机器持续同步 release 分支聚合出「预发合并态」，新提交喂给云端 Agent 分析 | 信噪比高；还原了「谁的开发机都没有的」最终环境 | 需一台独立机器 + 云端 Agent | 倾向采纳 |

## 4. 技术方案

<!-- [技术方案] 阶段重点。触发升级信号后再细化。 -->

三件事闭环（架构骨架）：

1. **代码环境还原** —— 持续把线上/预发两套工作区的所有子仓同步到各环境最终态；
   每个子仓**各自自动发现最新 release 分支**（按 committerdate 倒序），不是统一切一个分支；
   持续轮询（预发更快，如 300s），不需要人告诉它「这周预发分支叫什么」。
2. **业务逻辑冲突检测** —— 预发拉到新提交，把「谁改了什么」（按仓库分组、
   突出提交人名字——**「谁改的」是排查冲突的第一线索**）+ 完整代码喂给云端 Agent。
3. **告警闭环** —— 冲突沉淀为可流转记录，不停留在「群里发条告警」：
   `待回复 → 问题存在 / 误报 / 已修复`，状态流转同时校准 Agent 准确率。

设计原则：
- **本地守护进程零依赖、不内联任何 prompt** —— 易变的智能（prompt 编排）放云端 Agent，
  本地进程长期稳定不用改。
- **绝不阻塞和破坏本地工作区** —— 只读提取提交的作者/message/变更文件。
- **北极星指标：周冲突有效发现率**（Agent 报出的冲突里多少被人工确认为真问题），
  参考基准 >70%。只在真有合并风险时才 @ 责任人——这是信噪比的来源。

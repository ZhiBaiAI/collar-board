# blue-print — 蓝图探索层

> 这里是**未定型方案**的孵化区。成熟后「毕业」迁入 `docs/specs/` 成为正式 feature。

---

## 成熟度阶梯（命名即状态）

文件名前缀体现成熟度，**必须随进展改名**：

| 前缀 | 含义 | 典型内容 | 升级门槛 |
|---|---|---|---|
| `[调研]` | 还在看外部世界 | 竞品做法、可选技术、开放问题 | ↓ |
| `[讨论稿]` | 内部还没定 | 2-3 个候选方案 + 倾向 + 待决问题 | 至少 2 个候选方案，且能说清各自代价 |
| `[技术方案]` | 方案已定，待落地 | 架构、接口、数据、风险、排期 | 方案已选定，接口/数据/风险已明确 |

`[技术方案]` 后跟版本：`V1-MVP` → `V2` → `V3`……
版本代表**迭代轮次**，不是「第几稿 PPT」。

> **不要跳级** —— 没做过调研就直接写技术方案，方案大概率是空想。

---

## 完整生命周期

```
[调研] → [讨论稿] → [技术方案] V1-MVP → … → 毕业 → docs/specs/…/spec.md (feature)
                                              ↓
                                      → feature → patch → sunset
```

一个模块可以同时处于多种状态：
新版本在预研（blueprint）、当前版是 feature、历史版累积了若干 patch、更老的版本已 sunset。
**这四种类型不是互斥阶段，而是并存的状态。**

---

## 毕业条件

- [ ] 方案已被认可（不是「我觉得」）
- [ ] 影响面与验收标准可写清
- [ ] 有人认领（站点地图认领表登记到人）

毕业动作由 `collar-specs` 承接：
1. 在 `docs/specs/NN_[业务地图]域/` 下建 feature 目录与 `spec.md`
2. 技术方案内容迁入，补上验收标准与影响面
3. 在蓝图文件顶部标注 **已毕业 → spec 链接**，保留文件作为历史上下文
4. 更新站点地图与认领表

> **毕业不是删除。** 蓝图记录的是「我们为什么选了这条路」，属于历史上下文。

---

## 僵尸蓝图处理

| 情况 | 处理 |
|---|---|
| 超过 ⟨60⟩ 天无更新且未毕业 | 标记 `[搁置]` + 搁置原因 |
| 明确结论「不做」 | 保留但标注 `[否决]` + **否决理由**，**不要删** |

> 未来有人重新提这个想法时，那份否决理由能省下几周。
> **否决理由比方案本身更有价值。**

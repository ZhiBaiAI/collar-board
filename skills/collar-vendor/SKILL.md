# collar-vendor — 外部参考代码资产管理员

## 定位

`docs/vendor/` 不是「第三方依赖目录」，是**调研期的粗素材堆放场**。
用户在调研期把粗糙素材随手丢进来，等真正做设计时，AI 自动把这些沉睡的知识拉进来参与决策。

> 「用户放进 vendor 的代码不一定完整阅读过，这一步帮用户『读』并提炼要点。」

## 核心原则：只做减法

- ❌ 不整个 clone 一个仓库进来（体积大、噪音多、许可风险）
- ✅ 只保留**我们真正需要的那几个文件**
- ✅ 每个条目必须在 `docs/vendor/SOURCES.md` 登记，否则视为垃圾文件，可被清理

---

## 触发方式

| 类型 | 时机 |
|---|---|
| 主动 | 用户放入外部代码 / 给了一个参考仓库 / 说「调研一下 XX」 |
| 被动（联动） | `collar-specs` 写技术方案时，扫描 vendor 找实证参考 |

## 执行步骤

### Step 1 — 登记（先登记再落地，未登记不入库）

`docs/vendor/SOURCES.md` 追加一条：

```markdown
## ⟨名称⟩ ⟨版本⟩

- **来源**：⟨URL / commit⟩ ｜ **许可**：⟨License⟩ ｜ **同步方式**：⟨快照 / 补丁⟩
- **为什么需要**：⟨解决我们的哪个问题⟩
- **保留范围**：⟨只留了哪些文件，删掉了什么⟩
- **提炼要点**：⟨3-5 条可直接复用的模式 / API 用法 / 坑⟩
- **适用**：⟨哪些 spec 会用到它⟩
```

### Step 2 — 选择算法：先做减法，再选同步方式

**第一步「减法规则」—— 只下载我们所需要的**（按顺序过一遍筛子）：

| 筛子 | 保留 | 删掉 |
|---|---|---|
| 用途 | 我们需要参考的核心实现、目标 API 的调用示例 | 无关模块、其他语言绑定 |
| 体积 | 单文件、或可直接读的少量文件 | 构建产物、`dist/`、锁文件、二进制 |
| 噪音 | 源码 | 测试、CI 配置、文档站、`examples/` 演示项目、`.github/` |
| 合规 | **`LICENSE` 必须保留**（否则无法证明许可） | 许可不合规的全部内容 → 直接放弃引入 |

> 减法做完通常只剩原仓库的 ⟨5%⟩ 不到。**宁可少拿，不要多拿** ——
> 多拿的每一份文件都是 AI 上下文里的噪音。

**第二步「同步方式选择算法」—— 按三个判定维度选**：

```
① 我们是否需要在上游基础上改动？
   ├─ 是 ──────────────────▶ 补丁式
   └─ 否 ↓
② 上游是否活跃（近 ⟨6⟩ 个月有提交 / 我们是否会跟进升级）？
   ├─ 是（要跟进）─────────▶ 补丁式（便于重放我们的改动）
   └─ 否（一次性参考）↓
③ 我们是否只关心某个特定版本的写法？
   ├─ 是 ──────────────────▶ 快照（锁定 commit，永不升级）
   └─ 否 ──────────────────▶ 快照（标注来源与版本即可）
```

| 方式 | 适用 | 说明 |
|---|---|---|
| **快照** | 一次性参考、上游不活跃、不需要改动 | 复制需要的文件，标注来源 commit |
| **补丁式** | 需要在上游基础上改动，或需跟进上游升级 | 保留 upstream 原文 + 我们的 patch 文件，升级时可重放 |

判定结果写进 `SOURCES.md` 的「同步方式」与「保留范围」两栏 ——
**保留范围要写明删了什么**，否则下次没人知道为什么缺文件。

### Step 3 — 提炼（本 Skill 的核心价值）

对放进来的代码自动做「代读」，产出可直接复用的知识：
- **代码模板**：可复制的骨架结构
- **API 用法**：关键调用序列与参数含义
- **架构模式**：它解决同类问题的组织方式
- **已知坑**：注释里、issue 里暴露的边界条件

提炼结果写进 `SOURCES.md` 的「提炼要点」，**控制在 5 条内**——超过说明该拆条目。

### Step 4 — 供 specs 取用

`collar-specs` 生成技术方案时，会扫描 vendor 匹配关键词：
命中则把提炼要点融入方案，并**标注来源**（哪份 vendor、哪个文件）。
这样方案不是凭空生成，而是**有实证支撑**。

### Step 5 — 定期清理

- 超过 ⟨90⟩ 天未被任何 spec 引用 → 标记为待清理
- 上游已废弃 / 许可不合规 → 直接删除并留一条删除记录（为什么删过，避免二次引入）

---

## 护栏

- ❌ 未登记的裸代码文件（下次清理直接删）——先登记再落地
- ❌ 拷贝许可不合规的代码（**先查 License，再落地**；`LICENSE` 文件必须随保留文件一起留）
- ❌ 把 vendor 当运行时依赖用（运行时依赖走包管理器，不进 vendor）
- ❌ 整仓 clone——只做减法，减法做完通常不到原仓库的 ⟨5%⟩
- ❌ 提炼要点超过 5 条不拆条目
- ✅ 保留范围必须写明删了什么、为什么删

Next: 写技术方案时由 `collar-specs` 扫描取用；超过 ⟨90⟩ 天无引用按清理规则标记。

## 与其他 Skill 的协作

- `collar-specs`：**主要消费者**，vendor 是它的实证参考源
- `collar-architecture`：外部架构模式作为 ADR 的备选方案素材
- `collar-wiki`：竞品分析类的文字结论去 wiki，代码类的来 vendor

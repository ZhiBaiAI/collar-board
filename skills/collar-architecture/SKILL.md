# collar-architecture — 架构事实、原则与决策

## 定位

回答一个问题：**这个项目为什么长这样。**
代码告诉你 what，Spec 告诉你 intend，architecture 告诉你 why。

`docs/architecture/` 里三样东西分工不同，别混写：

| 位置 | 回答 | 时态 |
|---|---|---|
| `README.md` 结构视图 | 系统此刻**怎样运转**（事实） | 只写现在时 |
| `principles/` | 这类问题**永远**怎么处理（不变量） | 只写现在时 |
| `ADR/` | 当时**为什么**这么选（因果） | 记录过去，只增不改 |

## 触发方式

| 类型 | 时机 |
|---|---|
| 被动 | git commit 中命中**结构性变动信号**（见下） |
| 主动 | 用户做技术选型、问设计理由、要求写 ADR、评估重构 |

结构性变动信号：
- 新增 / 删除模块或包；目录层级调整
- 接口签名变更（含字段增删改）
- 依赖新增、替换、升级大版本
- 数据模型 / 存储结构变更
- 引入新的外部系统或中间件

## 执行步骤

### Step 1 — 判定是否值得记 ADR

只记**不可逆或代价高昂的决策**。改个变量名不写 ADR，选数据库要写。
判断标准：**未来有人问「为什么不用 XX」时，能拿出来回答的，就值得记。**

### Step 2 — 写 ADR

路径：`docs/architecture/ADR/NNNN-简述.md`（四位编号，只增不改）

状态机：`proposed` → `accepted` → `deprecated` / `superseded by NNNN`；
提出后被否决的决策记为 `rejected`，**保留否决理由**——否则下个会话的 Agent
会把同一个被否方案当新方案重提一遍。

固定结构：
1. **背景**：要解决什么问题，约束是什么
2. **决策**：选了什么（一句话，加粗）
3. **备选方案**：至少两个 + 各自代价
4. **理由**：为什么是它（可量化优先）
5. **后果**：正面 / 负面 / 需要接受的代价
6. **Revisit 条件**：什么情况下该推翻这个决策

### Step 3 — 维护结构视图（只写现在时事实）

更新 `docs/architecture/README.md` 里的：
- 模块依赖图（谁依赖谁，禁止环）
- 接口契约清单（跨模块调用点、签名、负责人）
- 数据模型概览

**视图必须短**。细节放代码，这里只放「AI 通读全局时需要知道的骨架」。

**只写现在时**：写「X 依赖 Y」，不写「X 从 Z 改成了 Y」。
演进过程属于 ADR 与 changelog，写进结构视图会让读者分不清哪句是现状
（结构门禁 S7 拦截典型指代词）。

### Step 3.5 — 维护工程原则（principles/）

结构性变动若确立了**跨场景不变量**（幂等、一致性、超时、降级、兼容），
写进 `docs/architecture/principles/P-NNN-名称.md`（复制 `_template-principle.md`）：

- **什么进 principles**：回答「这类问题永远怎么处理」，极少变
- **什么进 ADR**：回答「当时为什么这么选」，随选型演进
- 原则变了是大事：必须另起 ADR 记录变更原因，并把旧原则标为「已修订」

原则与 ADR 冲突时，**先改原则再改实现**——原则是决策的上游。

### Step 4 — 上下文缝补检查（本 Skill 的关键职责）

任何架构变动都要问一句：**这次改动会不会让 AI 看不到某些东西？**

| 变动 | 上下文风险 | 缝补方式 |
|---|---|---|
| 提示词 / 配置外置到平台或 DB | 代码里只剩调用框架，AI 读不出行为逻辑 | 建**只读 MCP 通道** + 配套 Skill（何时查/怎么查/查到怎么用） |
| 逻辑外置到脚本平台 | 脚本内容不在仓库 | 用 `//!` **声明式注释保留锚点**：脚本名、风险等级、参数、可运行环境 |
| 引入环境差异（预发 ≠ 线上） | AI 排查时遇到无法解释的现象 | 在 `AGENTS.md` 关键约定速查表显式声明，细节沉淀 ADR |
| 引入代码生成 / 宏 / 编译期魔法 | 源码 ≠ 运行态 | 生成物可读化，或在 runbook 中给出还原方式 |

> **项目铁律：任何导致上下文异常的研发架构变动，都必须用适合的方式缝补缺损的上下文。**
> 完整协议见 `docs/runbook/context-stitching.md`。

未缝补即视为**架构缺陷**，必须在 ADR 的「后果」里显式登记为技术债。

### Step 5 — 自检

- [ ] ADR 有备选方案和代价（不是「选型报告」，是「决策记录」）
- [ ] 被否决的决策标了 `rejected` 且保留理由（防止未来重提）
- [ ] 结构视图已同步，足够短，且只写现在时事实
- [ ] 新确立的跨场景不变量已进 `principles/`（模板 + 正反例）
- [ ] 上下文缝补已确认（无风险 / 已缝补 / 已登记为债，三选一）
- [ ] 与相关 spec 双向链接

Next: 决策落地后在 changelog 留痕；环境差异移交 `collar-runbook` 落 `environments.md`。

## 护栏

- ❌ 改写已有 ADR 正文——决策记录只增不改，推翻用新 ADR 或标 `superseded`
- ❌ 删掉被否决的决策——`rejected` + 理由必须保留（防未来重提同一方案）
- ❌ 结构视图写演进过程（「X 从 Z 改成了 Y」）——只写现在时，演进归 ADR/changelog
- ❌ 先改实现再改原则——原则与实现冲突时先改原则（上游），原则变更必须另起 ADR
- ❌ 上下文缺损未缝补就静默交付——必须在 ADR「后果」显式登记为技术债
- ❌ ADR 没有备选方案和各自代价——那是选型报告，不是决策记录

- `collar-vendor`：外部框架的架构模式提炼进来作为备选方案素材
